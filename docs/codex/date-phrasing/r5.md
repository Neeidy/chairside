**The universal defence does not hold. I found three HIGH counterexamples:** an inherited confirmation without a year, a concurrent turn that changes the last confirm shown, and a confirmation response that is never delivered. The ordinary sequential paths show the year correctly.

All probes and logs are in [.audit-r2d](/home/auditor/work/.audit-r2d). No tracked files changed.

1. **HIGH — A pending confirmation from before R2d can write without any year-bearing ask.**

   Location: staged Main, **Build Event Request**, **Build Reschedule Event Request**, and their confirmation routers.

   Scenario: a conversation reaches `confirming` before deployment. Its customer saw:

   ```text
   Haircut, Thursday 5 Nov 11:00 for Kim — shall I book it? (yes / no)
   ```

   After switching to the staged export, the customer sends `yes`. The booking builder accepts the persisted stage and slots; it neither checks which confirm format was shown nor issues a replacement ask.

   Command:

   ```sh
   node .audit-r2d/probes.cjs
   ```

   Output:

   ```text
   LEGACY old ask: Haircut, Thursday 5 Nov 11:00 for Kim — shall I book it? (yes / no)
   LEGACY staged writes: [ '2026-11-05T10:00:00.000Z' ]
   ```

   The probe creates the pending state using `267d9b1`’s export, then confirms using HEAD’s staged export. The reschedule router likewise has freshness and target checks, but no evidence that its pending ask contained years.

2. **HIGH — Overlapping turns can write a slot different from the last confirm shown.**

   Location: staged Main, **Load State → Validate Intent → Build Event Request → Book Appointment**; **Save State**.

   Concrete interleaving for one sender, using different message IDs:

   - The customer has seen a confirm for **5 November 2026**.
   - Execution A processes `yes` and reads that stored slot.
   - Before A inserts, execution B processes `haircut 6 november 11:00 Kim`, saves it and shows a confirm for **6 November 2026**.
   - A resumes and inserts **5 November**, then writes its appointment row.

   Command:

   ```sh
   node .audit-r2d/probes.cjs
   ```

   Output:

   ```text
   RACE last shown: Haircut, Friday 6 Nov 2026 11:00 for Kim — shall I book it? (yes / no)
   RACE writes: [ '2026-11-05T10:00:00.000Z' ]
   ```

   The offline probe uses two replay instances sharing the store and pauses A immediately before `Book Appointment`. Production node bodies are unchanged.

   Message-ID deduplication does not serialize different messages. Calendar verification checks overlapping events, not whether the customer has since received another confirm.

   The general concurrency limitation is already recorded in `docs/ARCHITECTURE-DECISIONS.md:96`. This finding concerns its concrete violation of R2d’s new **last-confirm-slot guarantee**, not the previously recorded double-`yes` case.

3. **HIGH — Saving confirmation state does not establish that the ask was shown.**

   Location: staged Main, **Save State → Build Reply Payload → Send Reply To Origin → Finalize Outbound**; **Outbound Send Failed**.

   Scenario: Save State commits `stage=confirming`, but the widget response is lost before reaching the customer. A subsequent `yes` inserts the persisted slot although no confirm was received.

   Command:

   ```sh
   node .audit-r2d/probes.cjs
   ```

   Output:

   ```text
   LOST RESPONSE simulated response transport failure persisted stage= confirming
   LOST RESPONSE writes: [ '2026-11-05T10:00:00.000Z' ]
   ```

   This injects a transport failure immediately before the widget response. The corresponding WhatsApp failure branch only marks `zernio_send_failed` and alerts; it does not invalidate confirmation state. A duplicate delivery also does not recover the missing ask: `Idempotent Replay` returns `duplicate_ignored` without replaying the original response.

   The recorded at-most-once delivery cost does not support the stronger R2d claim that the confirm was **shown before every write**.

For question 1, I traced the write paths as follows:

| Path | Trace and result |
|---|---|
| Booking | `Compute Availability` builds the year-bearing ask and saves `confirming`. A later confirm reaches `Build Event Request`, which reads **stored** slots from `Validate Intent`, then `Book Appointment`. |
| Booking mirror | `Verify Slot → Check Race → Race Gate → Write Appointment`; the SQL parameters use `Build Event Request.booking`, preserving that execution’s slot. |
| Reschedule | `Compute Reschedule Availability` shows both dates with years and saves the proposed slot, target and confirmation turn. A confirm passes `Reschedule Fresh?`, target lookup/validation, then `Build Reschedule Event Request → Book Reschedule Appointment`. |
| Reschedule mirror | Verification precedes `Update Appointment (Reschedule)`, which uses the constructed booking’s UTC times; deleting the old event follows the update. |
| Verify, race-lost, orphan | These occur **after the insert**. They retain or delete that execution’s event; none selects a replacement slot. Verify-unavailable can retain the inserted event without a mirror update. |
| Insert retry/reconciliation | Booking reconciliation checks the deterministic event ID and returns through verification or handoff. It supplies no additional confirmation-delivery or freshness guarantee. |
| Other intents and stages | Reviewed collection, FAQ, lead, uncertain/extraction-failure turns, cancel/reschedule aborts and handoff routes. The sequential replay covers eleven intervening-turn variants on both lanes. |
| Guards and duplicates | Kill-switch/max-turn guards and handoff lock stop the normal execution before writing. Duplicate-message routing skips the write lane. They do not revoke an execution already in flight. |

Thus the ordinary builders preserve their execution’s stored slot, but that is weaker than “the last confirm shown to this customer.”
