1. **MEDIUM — A legacy or purged confirmation can book without a name.**

   **Location:** staged Main, `Build Event Request`; `tests/unit/name-capture.test.cjs`, test “Build Event Request: the title and booking.customerName carry the KEPT name”.

   **Scenario:** deploy while an existing conversation is already `stage='confirming'`, with service/date/time but no `slot_name`. The customer answers “yes”. Alternatively, Purge clears the name from an abandoned confirmation whose booking date is still in the future.

   The confirm lane bypasses `Slot Gate`. `Build Event Request` checks stage/date/time, but does not require a name. It emits a valid event ID, a nameless title, and `customerName: null`. A new appointment can consequently be inserted with no name.

   **Reproduction:**

   Observed:
   ```text

   {"eventId":"7769…","summary":"Haircut (bot)","customerName":null}
   ```

   Migration-before-Main prevents missing-column errors, but does not address these existing conversations. This is separate from the recorded acceptance of date changes during confirmation.

   **Test gap:** the existing event-builder test explicitly expects the nameless case to produce `Haircut (bot)`. It therefore endorses this violation of “a booking must carry the customer’s name”; the mutants do not cover legacy or purged confirmations.

2. **MEDIUM — Purge leaves the customer’s name in `computed_reply`.**

   **Location:** staged Main, `Compute Availability` and both Save States; staged Purge, `Scrub Recent Messages`; [privacy page](/home/auditor/work/web/site/app/privacy/page.tsx).

   **Scenario:** the customer supplies `Retentioncanary`, receives the booking confirmation question, then leaves the conversation inactive for 31 days.

   `Compute Availability` embeds the name in `computed_reply`. Save State persists that reply. Purge clears only `recent_messages` and `slot_name`, leaving the reply—and thus the name—in the conversation indefinitely.

   **Reproduction:**
   ```sh
   node audit-tmp/probe.cjs
   ```
   Observed:
   ```text
   persisted computed_reply:
   Haircut, Monday 7 Jan 11:00 for Retentioncanary — shall I book it? (yes / no)

   purge SET: SET recent_messages = '', slot_name = NULL
   ```

   The remaining row still contains that confirmation text. Purge’s RETURNING projection also includes `computed_reply`, so the name can enter the Purge execution data through this field.

   This contradicts D-2’s reason that the conversation must not retain the name longer than its messages, and the privacy statement that the name is erased after 30 days. Retaining an assistant reply is documented; retaining the newly embedded name despite the explicit erasure promise is not an accepted bound.

   **Test gap:** the name, privacy and mutant suites remain green. They check the named columns and SQL fragments, but do not follow the name into the persisted reply.

**Answers to the five questions**

**1. Name handling / CRT #16**

Within the recorded bounds, the deterministic fill behaves as described:

- It preserves explicit `handoff`, `cancel`, `reschedule`, FAQ, lead and confirm intents.
- It excludes pending cancel/reschedule confirmations.
- It excludes a detail-bearing `book` turn, invalid model output and a conflicting sanitised model name.
- The sanitizer copies are byte-equal; the tests execute them and cover controls, format/zero-width/bidi characters, digits, markup, the 40-code-point cap and A2 names.

`node audit-tmp/probe.cjs` additionally confirmed the explicit-intent and pending-confirm exclusions, A2 examples, and the usual D-3 refusal sequence.

A non-name can still be accepted: **“Dance with dolphins”**, classified `unknown` at the name ask, becomes a high-confidence booking name. This is the explicitly accepted deny-list bound in acceptance 2b, so I am **not reporting it as a finding**.

The kept slot value is not interpolated into later LLM requests. `Build LLM Request` sends only `provided`/`missing`. Owner alerts omit it from their slot facts, but can contain the original name-bearing customer message through `recent_messages`, as declared in deviation 7.

D-3 works for its declared detail-less `book`/`unknown` refusal path. It is not a blanket second-turn rule across topic changes or booking details. I found no additional false escalation within that scope. Finding 1 shows that name enforcement can nevertheless be bypassed on the confirmation lane.

**2. Booking write / #1b**

The event-builder change reads the kept name; the appointment change preserves an existing name when the incoming name is NULL or empty. Neither changes the deterministic booking key, event ID construction, write-then-verify graph, race detection or yield paths.

I found no new cross-sender name write. The confirmed slot state is sender-scoped, and the event key still contains `sender_key`. A nonempty incoming name can replace a prior name, consistently with the declared fresh-name-wins rule.

The defect is **Finding 1: a new booking can still be nameless**. The COALESCE protects an existing appointment name; it cannot supply a name for a new row.

**3. Reschedule / #8**

No changed booking-selection or ownership check was found.

`Validate Reschedule Target` adds the name only after selecting the exact `cancel_target_id` from the sender-filtered query results. `Build Reschedule Event Request` uses that selected appointment’s name. `Reschedule Lookup` preserves conversation slots, but does not use their name to choose the booking or title the moved event.

The reschedule update still does not overwrite `customer_name`. These changes do not introduce another sender’s name.

**4. Store and retention**

`Load State` reads `slot_name`; both Save States write and update it, sending NULL when absent. Their RETURNING projections do **not** include `slot_name`, despite §3.2 naming RETURNING; subsequent turns reload it through `Load State`, so I found no functional loss from that omission.

Purge correctly finds an old row whose messages are already empty but whose `slot_name` remains, and clears that column. **Finding 2 means the overall name-erasure claim is still false.**

The migration adds nullable text without a default, transactionally checks its shape and app privileges, and checks that `salon_ro` has SELECT but lacks UPDATE. Its read-only check does not test INSERT privilege, so it is narrower than the R1 prose’s unrestricted “cannot write” claim; the committed role setup grants `salon_ro` SELECT only.

Migration → Purge → Main is sufficient for the new SQL’s column dependency. It is insufficient for the name requirement because existing confirmations need handling, as Finding 1 demonstrates.
